# Public research portfolio: priority-weighted coverage and causal discipline

**Status: proposed public-only contributor guidance.** Not an autonomous scheduler, an executive priority engine, a work-queue grant, a completion oracle or a deployed capability. The purpose is to keep every relevant research domain under review without distributing engineering labor uniformly irrespective of importance.

Public issues and source history are collaboration evidence; they cannot grant privileges to a separate private project.

## Coverage and priority are separate dimensions

The [Community Tracks](COMMUNITY_TRACKS.md) guide and the [Research Hub](research-hub.html) describe SIX strategic research domains: **blockchains/interoperability, cryptography, privacy, AI/automation, communications, and security/software trust**. Website/contributor experience is a cross-cutting support lane, not another strategic research domain.

Use one primary domain per issue for counting, with optional secondary topic labels. A chain/privacy/cryptography issue does not count as three separate completed implementations.

- **Coverage review:** every relevant domain gets a source-grounded check for missing scope, recent substantive evidence, unresolved assumptions, and an independently valuable next question. No open issues means REVIEW_SCOPE, not proof of neglect or a command to build something.
- **Priority-based engineering:** allocate execution to verified high-value prerequisites, integrity and safety work, causal leverage and bounded tasks with source and permission gates. Do not turn a desire for balance into equal engineering hours or quota-driven busywork.
- **Comparably ranked tasks:** after higher-priority constraints, prefer a currently under-reviewed domain when work is source-ready and noncolliding. Missing status or work effort remains UNKNOWN; it is not a zero score.

## Distinguish causal types before sequencing

| Relation | What it establishes | What it does not establish |
| --- | --- | --- |
| Explicit public pre-merge review gate | A review requirement for a named public effect | Protected execution authority, general project priority or all hard work dependencies |
| Independently qualified hard prerequisite | A specifically evidenced AND/OR requirement for a task | That every citation is a blocking dependency |
| Source/provenance dependency | A claim needs exact evidence from another artifact | That the upstream source is a completed work item |
| Related/coordination | Contributors should compare outcomes and avoid path collisions | A hard dependency or permanent issue owner |
| Structural parent | Where an item belongs in the domain taxonomy | Proof of causal necessity |
| Observed result | An exact source/test/release proves its limited behavior | Production readiness, owner identity or an accepted task lease |

Never promote graph adjacency, shared code ownership, issue labels or parallel source references into verified hard prerequisites. Record unknown sources and contradictory evidence explicitly.

## Source-based work selection

For a candidate increment, apply these gates in sequence:

1. **Integrity and publication boundary:** independent public rights classification, complete path allowlist, exact source/branch/PR collision review, permission scope, negative tests, no secrets or private work history. HOLD unqualified effects.
2. **Actual dependencies and unblock value:** identify named and evidenced high-impact prerequisites. A proposed edge is not sufficient to schedule work.
3. **Accepted priority evidence:** cite a reviewed reason/source/date. If not available, priority stays UNKNOWN; do not manufacture a numerical merit score from issue counts or recency.
4. **Marginal benefit and resource cost:** prefer narrow reusable source improvements, integrity tests and independently demonstrated functional advances over speculative breadth and repeated decorative work.
5. **Anti-starvation among comparable eligible tasks:** prefer an under-reviewed domain when priority, source quality and readiness are comparable; never override a proven safety blocker to satisfy a quota.
6. **One scoped reviewable contribution:** verify issue and exact branch/base/head, allowlisted files and current PRs, then publish only with the usual human rights and maintainer review. Leave reproducible test evidence and a durable handoff.

Before anyone claims a ranked priority, the record needs: stable issue ID, reviewed primary domain, source generation/date, exact goal, publication class, intended effect, genuine AND/OR prerequisites with source, progress evidence, cost/resources, active overlap and a reviewed priority rationale. Missing producer metadata is UNKNOWN, not a default high/low score.

## Review all domains without creating a second control plane

At each substantive public milestone or planned portfolio review, record for each of the six research domains its last independently verified public result (or UNKNOWN), latest evidence gaps, source-linked issue(s), meaningful next review question, dependencies and current contributor/PR conflicts when observable. Do not infer that a GitHub unassigned issue has no active worker. Avoid inventing an always-on monitoring process merely to generate coverage metrics.

For an empty domain: either draft a bounded falsifiable research invitation, record why no justified task exists, or mark it deferred with a review trigger. For an already-covered domain, do not generate low-value issues purely to make bars equal. Keep the six-domain **review obligation** separate from actual implementation allocation.

Another authorized priority/causal system may consume independently qualified public issue metadata through its own permission boundary. This document does not duplicate that system, transfer private scores, expose internal architecture, authenticate workers, activate a repository bot or create any execution grant. A private or protected project must adopt public inputs through its own evidence, collision and authority checks.

**Adoption:** draft public-origin guidance only. An actual repository policy change requires a bounded PR and positive provenance/security review. A source draft and local test do not imply that any contributor or private system adopted the procedure.
